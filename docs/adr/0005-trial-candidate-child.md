# ADR-0005: Ребёнок-кандидат для пробного занятия

## Статус

Предложено для согласования с Анель в TRU-100.

## Контекст

`LessonService.enroll()` и все потребители состава занятия работают с
`Child`. У новой заявки ребёнка в базе ещё может не быть, а в заявке для
MVP хранятся имя и возраст, но не точная дата рождения и пол.

## Решение

- При первой записи заявки на пробное создаётся `Child` со статусом
  `trial` («Пробный»). `LessonService` продолжает принимать только Child.
- Дата рождения временно рассчитывается из указанного возраста на дату
  записи и получает признак `birth_date_is_estimated=True`. Пол может быть
  пустым до уточнения у родителя.
- Пробный ребёнок связан с заявкой через `LessonEnrollment.source_lead`.
  У одной заявки может быть только одна активная запись, отменённые записи
  сохраняются для истории и будущего переноса в TRU-105.
- При ручном сохранении даты рождения признак приблизительности снимается.
- Сервис дублей продолжает считать заявку основным телефонным совпадением:
  пробный Child не создаёт отдельного родителя и телефон. При конвертации
  TRU-102 должен либо активировать этого Child, либо объединить его с
  найденным существующим ребёнком.

## Отвергнутые варианты

- Передавать `Lead` прямо в `LessonService`: ломает единый тип участников и
  заставляет посещаемость, вместимость и календарь обрабатывать две модели.
- Подставлять вымышленный пол или считать приблизительную дату точной:
  создаёт недостоверные персональные данные без явной пометки.
- Создавать обычного активного Child: пробный преждевременно попадает в
  метрики действующих учеников.

## Последствия

- В списке детей появляется отдельный статус «Пробный».
- TRU-102 обязан снять статус `trial`, уточнить дату/пол и обработать дубли.
- TRU-105 использует `source_lead` и мягкую отмену `LessonEnrollment`, не
  создаёт нового кандидата при переносе.

## Списание пробного (TRU-101)

Для стыка с TRU-71 зафиксирован отдельный технический исход
`trial_no_charge`: при отметке пришедшим активная запись
`LessonEnrollment(kind=trial)` не вызывает `SubscriptionService.consume`,
не выставляет `no_subscription_flag` и не вызывает создание задачи
администратору. Это не ошибка отсутствующего абонемента, а ожидаемое
бесплатное пробное занятие.

Контракт покрыт тестом `test_trial_attendance_does_not_charge`, включая
проверку, что точка создания задачи «ребёнок без абонемента» не вызывается.
Если в TRU-71 заглушка задачи будет заменена реальной моделью, менять этот
контракт на стороне посещаемости не потребуется.
