# Нагрузочное тестирование (TRU-155)

## Цель

Проверить бюджет ТЗ п. 10.2: **p95 не больше 1 секунды** для списка детей,
недельного календаря, журнала посещаемости и приёма оплаты. Среднее время
не используется как критерий. Профиль моделирует 20 одновременно работающих
устройств в пиковую минуту центра.

Между действиями каждого виртуального сотрудника — 2–5 секунд на чтение
экрана. Это даёт пиковую одновременность 20 устройств, но не превращает
сценарий в бессмысленное непрерывное прокликивание API.

Инструмент — **Locust**. Он выбран потому, что проект и генераторы данных уже
на Python, а профиль может использовать те же модели только для подготовки
идентификаторов. Измеряемые действия всегда выполняются через HTTP API.
Runner сам поднимает отдельный production-подобный Gunicorn на восемь workers:
результаты не зависят от однопроцессного Django `runserver`, используемого в
локальной разработке. Параметр `--host` оставлен только для замера отдельного
стенда.

## Целевой набор

`seed_analytics` остаётся единственным генератором больших данных:

- 10 филиалов;
- 5 000 детей;
- 100 сотрудников;
- 250 групп × 2 занятия = 500 занятий в неделю;
- год занятий, посещений, абонементов, оплат и заявок;
- ещё 499 небольших организаций для проверки tenant-фильтрации на общей БД.

Генератор изолирован слагами `analytics-volume` и `load-scale-*`. `--reset`
архивирует только эти организации и не удаляет демо-центр.

## Запуск одной командой

Сначала пересоберите backend после изменения зависимостей:

```powershell
docker compose build backend
```

Полный целевой прогон, включая сравнение глобального `random_page_cost`:

```powershell
docker compose run --rm backend python loadtests/run.py --seed --organizations 500 --users 20 --duration 2m --compare-random-page-cost
```

Команда:

1. пересоздаёт целевой набор;
2. запускает Locust для текущего значения PostgreSQL;
3. временно глобально ставит `random_page_cost = 1.1`, перезагружает конфиг и
   повторяет профиль;
4. обязательно восстанавливает исходное значение в `finally`;
5. записывает p50/p95 и число ошибок в `docs/load-testing-results.md`;
6. сохраняет подробные CSV/HTML локально в `backend/loadtests/results/`
   (они исключены из Git).

Быстрый smoke без пересоздания данных:

```powershell
docker compose run --rm backend python loadtests/run.py --users 4 --spawn-rate 4 --duration 20s
```

Locust создаёт реальные оплаты по 1 ₸, но только в организации нагрузочного
сида. Это проверяет именно полный write-path приёма оплаты, а не безопасный,
но нерепрезентативный GET.

## Профиль пиковой минуты

| Действие | Вес | API |
| --- | ---: | --- |
| Открыть журнал занятия | 4 | `GET /api/v1/attendance/roster/` |
| Открыть календарь на неделю | 3 | `GET /api/v1/schedule/` |
| Открыть список детей | 3 | `GET /api/v1/clients/children/table/` |
| Принять оплату | 1 | `POST /api/v1/payments/` |

JWT создаётся до старта измерения. Время входа и rate limit формы входа не
смешиваются со временем основных экранов.

## Разбор превышений

Для каждого действия с p95 > 1000 мс создаётся отдельный тикет. В описание
прикладываются строка из Locust CSV и план проблемного SQL:

```sql
EXPLAIN (ANALYZE, BUFFERS, VERBOSE) <запрос>;
```

Оптимизация не смешивается с нагрузочным тикетом: так остаются отдельно
воспроизводимый baseline и изменение, которое его улучшает.

## Нестабильный unit-тест

`tests_child_list_performance.py` остаётся диагностикой числа запросов и
одиночного worst-case, но не является нагрузочным gate CI: общие GitHub
runner'ы давали 3,3 с при повторном успешном прогоне. Приёмочный бюджет
проверяется Locust-профилем на выделенном Postgres; unit-тест запускается
последовательно и не маскирует p95 под нагрузкой.
