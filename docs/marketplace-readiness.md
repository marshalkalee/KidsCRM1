# Готовность данных к B2C-маркетплейсу

Ревизия 07.10.2026 (TRU-177). ТЗ п. 12 выносит маркетплейс («1Fit для
детей») за рамки проекта, но требует, чтобы модель данных и API уже сейчас
были пригодны для внешнего потребления: свободные места, возраст,
расписание. Здесь записано, что есть, чего нет и сколько стоит добавить
сейчас по сравнению с «потом», когда в системе будет 500 центров.

## Принцип

Наружу уходит **только предложение центра** — и только то, что центр сам
отметил публичным. Детей, родителей, посещаемость и деньги семей публичный
срез не содержит ни при каких условиях (тот же принцип, что у агрегатов
для ИИ, TRU-158). Без согласия центра в каталог не попадает никто:
признак публичности по умолчанию выключен.

## Что есть

| Нужно маркетплейсу | Где в системе | Состояние |
|---|---|---|
| Группа, направление, вместимость | `Group` (TRU-39) | Есть |
| Возраст | `Group.age_min`, `age_max` | Есть. Наружу — только диапазон группы, не возраст детей |
| Расписание | Шаблоны `ScheduleTemplateSlot` и занятия `Lesson` (TRU-41, TRU-43) | Есть. Срез отдаёт конкретные занятия; регулярный вид «вт/чт 17:00» строится из шаблонов |
| Свободные места на занятие | `public_api/catalog.py → offer()` | **Добавлено в TRU-177.** Одним запросом на период |
| Цена | `SubscriptionType.price` (TRU-57) | Есть. Публикуется только при `is_public` |
| Признак «показывать публично» | `Group.is_public`, `SubscriptionType.is_public` | **Добавлено в TRU-177**, по умолчанию выключено; галочки в формах группы и типа абонемента |
| Филиал и адрес | `Branch.name`, `address` | Есть, но адрес — свободный текст |

## Свободные места: замер

`offer()` считает места одним запросом на весь период (подзапросы вместо
`participants()` на каждое занятие). Тест сверяет результат с
`Lesson.participants()`, включая отработки поверх группы, отменённые
записи и ребёнка, записанного и в группе, и поверх неё.

Замер на центре с годом данных (5000 детей, 250 групп), все группы:

| Период | Занятий | Запросов к базе | Время |
|---|---|---|---|
| 1 день | 63 | 2 | 30 мс |
| 7 дней | 479 | 2 | 89 мс |
| 31 день | 2 143 | 2 | 279 мс |

Число запросов не растёт с числом занятий — это тоже проверяет тест.

## Будущий адрес в публичном API

Когда маркетплейс начнут строить, срез открывается адресом публичного
API (`docs/public-api.md`), версия 1.1 — добавление адреса не ломает v1:

    GET /api/public/v1/catalog/?date_from=…&date_to=…

Бронь места на пробное (TRU-180) — там же, тоже v1.1:

    POST /api/public/v1/catalog/bookings/   {lesson_id, parent_name, phone, child_name, child_age}

Под капотом — `schedule.holds.hold_seat()`: заявка с источником «Маркетплейс»
и бронь на `HOLD_HOURS` (24 ч). Ответ — срок брони или текст `HoldError`
(«Свободных мест нет» и т. п.). Центр подтверждает обычной записью на
пробное из карточки заявки; не подтвердил — бронь истекает сама.

Ответ — список занятий публичных групп, поля строго из
`catalog.LESSON_FIELDS`: `lesson_id`, `starts_at`, `ends_at`, `group`
(название, направление, возраст, пробное: есть ли и цена), `branch` (название, адрес), `capacity`,
`free_seats`, `prices` (только публичные типы абонементов).

Доступ для маркетплейса — отдельный вопрос продукта: это не ключ центра
(Enterprise), а доступ платформы ко всем центрам, согласившимся на
публикацию. Решать при проектировании маркетплейса.
