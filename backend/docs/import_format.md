# Импорт детей — шаблон файла и спецификация формата

Тикеты: «Импорт: шаблон файла и спецификация формата» (ТЗ п. 4.1, п. 13.4,
критерии приёмки п. 11.1 и 11.3) и «Импорт: загрузка файла, парсинг и
маппинг колонок» (ТЗ п. 4.1, п. 10.1).

Второй тикет заменил фиксированные колонки на маппинг: администратор
грузит файл **как есть** (`.xlsx` или `.csv`), система угадывает
соответствие колонок по названию, остальное поправляется мышью на экране
маппинга (`domains/people/clients/column_mapping.py`). Таблица ниже —
по-прежнему список полей, которые система умеет распознать, и правил
очистки значений; колонки файла больше не обязаны называться ТОЧНО так,
как в шаблоне для скачивания.

## Статус — открытый риск, зафиксированный сознательно

ТЗ прямо требует получить **настоящие** Excel-файлы True Ballet до
проектирования шаблона (Discovery, открытый вопрос №4) — «проектировать
импорт по воображаемому формату — гарантированная переделка». Реальные
файлы не получены: они конфиденциальны, а получить их оказалось не
быстрее, чем предполагалось. По явному решению (обсуждение с Анель,
2026-09-21) шаблон и парсер спроектированы и проверены на **синтетических**
файлах, нарочито воспроизводящих грязь, перечисленную в самом тикете:

- объединённые ячейки (родитель на несколько строк своих детей);
- несколько телефонов в одной ячейке через запятую;
- «мама Айгерим» вместо чистого ФИО;
- даты в разных форматах;
- пустые строки-разделители между группами.

Из четырёх критериев приёмки тикета закрыты два (шаблон покрывает
перечисленную грязь; решение по остаткам абонементов принято и
описано ниже). **Не закрыты и не могут быть закрыты без центра:**
«реальные файлы получены и разобраны» и «список несохраняемых полей
согласован с центром». Как только реальные файлы (или их анонимизированная
копия) появятся — прогнать их через парсер и обновить этот документ, а
не считать задачу технически завершённой без этого шага.

## Формат файла

Колонки распознаются по названию через маппинг (не по позиции и не по
точному совпадению с шаблоном — администратор может назвать их по-своему).
Откуда берётся сырое значение для каждого поля (чтение `.xlsx`/`.csv`,
угадывание маппинга по алиасам) — `column_mapping.py`
(`SYSTEM_FIELDS`/`FIELD_ALIASES`); как значение очищается и валидируется —
`import_service.py` (`build_row`). Шаблон для скачивания (для тех, кто
предпочитает готовые названия колонок) собирается
`scripts/build_import_template.py` → `static/site/files/child_import_template.xlsx`.

| Колонка                | Обязательна | Формат                                                                                            |
| ----------------------- | ----------- | -------------------------------------------------------------------------------------------------- |
| ФИО ребёнка             | Да          | Текст                                                                                               |
| Дата рождения ребёнка   | Да          | `ДД.ММ.ГГГГ`, `ДД/ММ/ГГГГ` или `ГГГГ-ММ-ДД` (плюс нативная дата Excel)                             |
| Пол ребёнка             | Да          | `М`/`Ж` (также «мужской»/«женский», без учёта регистра)                                            |
| ФИО родителя            | Да          | Текст. Роль-префикс распознаётся автоматически («мама Иванова Марина» → ФИО «Иванова Марина» + роль «мама») |
| Телефон родителя        | Да          | Казахстанский номер; несколько через запятую/точку с запятой/слэш/«и» — сохраняются все            |
| Роль родителя           | Нет         | мама/папа/опекун/бабушка/другое. Явная колонка приоритетнее роли из префикса имени                 |
| Медицинские заметки     | Нет         | Текст — копируется в `Child.medical_notes` как есть                                                |
| Остаток занятий         | Нет         | Число — **не создаёт абонемент**, см. раздел про остатки ниже                                       |

Пустые строки (все ячейки пустые) пропускаются молча — это разделители
между группами в исходном файле, не ошибка.

### Что уже устойчиво к грязи (проверено синтетическими файлами)

- **Объединённые ячейки.** Если ФИО/телефон/роль родителя объединены на
  несколько строк (второй ребёнок той же семьи без повторного ввода
  родителя), парсер подставляет значение из строки-якоря объединения, а
  не читает эти строки как пустые.
- **Несколько телефонов в одной ячейке.** Каждый валидный номер
  сохраняется как отдельный `ContactPhone` — не только первый.
- **Роль внутри ФИО** («мама Айгерим»). Распознаётся и отделяется от
  имени; если отдельная колонка «Роль родителя» тоже заполнена — она
  главнее (осознанный ввод важнее угадывания).
- **Три формата дат** плюс нативная дата Excel — см. таблицу выше.
- Один "плохой" телефон среди нескольких в одной ячейке не проваливает
  всю строку — остальные валидные всё равно сохраняются.

### Известное ограничение

Синтетические файлы не могут воспроизвести *все* реальные аномалии
(опечатки в конкретных именах, нестандартные сокращения ролей,
специфичные для True Ballet группировки). Это причина, по которой
критерий «реальные файлы разобраны» остаётся открытым (см. «Статус» выше).

## Загрузка файла: .xlsx и .csv, маппинг колонок

- **Форматы.** `.xlsx` (через openpyxl, с разрешением объединённых ячеек)
  и `.csv`.
- **Кодировка и разделитель CSV определяются автоматически.** ТЗ прямо
  называет это нормой, а не исключением: файлы из Excel в Windows обычно
  приходят в `cp1251` с точкой с запятой. Порядок попыток декодирования —
  `utf-8-sig → utf-8 → cp1251`; разделитель — `csv.Sniffer` с запасным
  вариантом в пользу `;` (см. `column_mapping.CSV_ENCODINGS`/`_detect_delimiter`).
- **Автоугадывание маппинга.** Сначала точное совпадение заголовка файла
  с одним из алиасов поля (`FIELD_ALIASES`), затем — совпадение по
  подстроке для всех полей, которые не угадались точно. Один заголовок
  файла никогда не назначается двум полям системы одновременно.
- **Экран маппинга.** Слева — поля системы, справа — выпадающий список
  колонок файла (с уже проставленным угаданным вариантом); есть
  предпросмотр первых строк файла. Обязательные поля без пары блокируют
  переход дальше с явным списком, чего не хватает.
- **Сохранение маппинга.** Ключ — точный набор заголовков файла
  (`"|".join(headers)`), не имя файла: повторная загрузка файла с тем же
  составом колонок подставляет тот же маппинг автоматически, без
  повторной настройки (`ImportColumnMapping`).

## Фоновая обработка (ТЗ п. 10.1)

После подтверждения маппинга администратор видит сводку (сколько строк
распознано / не удалось разобрать) и запускает импорт. Сам импорт —
Celery-задача (`domains/people/clients/tasks.py:run_import_job`), не часть
HTTP-запроса: на файле в тысячи строк дедуп против базы
(`ChildService.find_duplicates` на каждую новую семью) не укладывается в
бюджет одного запроса. Строки к этому моменту уже разобраны и
провалидированы (синхронная, но дешёвая чисто-питоновская часть — разбор
файла, без обращений к базе); задача хранится и отслеживается как
`ImportJob` (`pending → running → done/failed`), администратор видит
статус на отдельной странице (обновляется вручную, без автообновления).

По этому тикету дедуп внутри фонового прогона автоматический — по тем же
правилам, что и раньше (дубль по телефону — пропуск, тот же телефон +
другой ребёнок — второй ребёнок в семье, иначе — новая запись), **без**
ручного выбора действия администратором построчно (как это было на
экране предпросмотра из предыдущего тикета): на файле в тысячи строк
построчная проверка нереалистична, человеческий контроль остаётся на
уровне экрана маппинга и сводки распознанных/нераспознанных строк.

## Поля, которые НЕ переносятся импортом

| Поле                                  | Перенос            | Почему                                                                                                                  |
| --------------------------------------- | ------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| История оплат                          | Не переносится      | Требует реальных `Subscription`/`Payment` с ценами, скидками, датами — восстановить из плоской таблицы ненадёжно; риск исказить финансовую историю выше пользы. |
| Абонементы (сам факт, тип, цена, срок) | Не переносится      | Та же причина — тип абонемента и цена в момент покупки не всегда есть в файле центра.                                    |
| Остаток занятий по абонементу          | **Да, но не автоматически** — см. ниже | См. отдельное решение: слишком важно для тихого игнорирования, но и не готово технически на этом шаге.                   |
| Расписание/группы/посещаемость         | Не переносится      | Домен Дарьи, отдельная задача импорта расписания при необходимости.                                                      |

**⚠️ Этот список зафиксирован технически, но не согласован с центром**
(см. «Статус» — это тоже часть незакрытого критерия приёмки). Прежде чем
реальный переезд состоится, список должен быть проговорён с True Ballet
явно, чтобы это не всплыло как сюрприз на приёмке.

## Решение по остаткам абонементов

Критерий приёмки MVP №3 (сверка остатков за две недели после переезда)
напрямую зависит от того, известен ли системе остаток на момент импорта —
если не перенести его, сверка обречена на несовпадение с первого дня не
по вине системы, а по вине неполных исходных данных.

**Решение:** колонка «Остаток занятий» в шаблоне есть, значение
**считывается и сохраняется в отчёте импорта** (администратор увидит
список «строка N (ребёнок): остаток — перенесите вручную»), но
**не создаёт `Subscription`/`SubscriptionLedgerEntry` автоматически**.

Причина: чтобы честно завести абонемент (а не просто число), нужны тип
абонемента, цена, дата начала/конца — этого в файле центра, скорее всего,
не будет в структурированном виде, и это домен Bekzat'а
(`domains/money/subscriptions/`), а не `people/clients`. Автоматически
придумывать эти поля значит выдумывать финансовые данные — хуже, чем
явно попросить администратора внести остаток вручную по отчёту.

**Не закрыто:** нужно решение Bekzat'а — либо (а) администратор заводит
остаток вручную через существующий экран продажи абонемента после
импорта по списку из отчёта, либо (б) отдельный, более узкий импорт
остатков в его домене (со своими обязательными полями — тип, цена, срок).
До этого решения критерий приёмки MVP №3 закрыть нельзя технически —
только организационно (ручной перенос по отчёту).

## Находки (синтетические файлы, не реальные — см. «Статус»)

Файлы строились по описанию грязи из самого тикета, не по наблюдению за
реальными данными True Ballet:

1. Объединение ФИО/телефон/роль родителя на несколько строк — воспроизведено,
   обработано (см. `_build_merge_lookup` в `import_service.py`).
2. Несколько телефонов в одной ячейке через запятую — воспроизведено,
   обработано (`_split_phones`).
3. «мама Айгерим» вместо ФИО — воспроизведено, обработано
   (`_split_role_prefix`).
4. Три формата дат — воспроизведено, обработано (`_DATE_FORMATS`).
5. Пустые строки-разделители — воспроизведено; уже обрабатывалось
   изначальной версией парсера (пустая строка пропускается без ошибки).

Что НЕ проверено (нет доступа к реальным файлам): нестандартные
сокращения имён/ролей на казахском, специфичная структура листов (один
лист на филиал/группу?), реальные примеры «испорченных» дат за пределами
трёх протестированных форматов, объём файла (сотни vs тысячи строк) и
связанное с этим реальное время разбора.
