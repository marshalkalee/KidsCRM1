# ADR-004: Фронтенд — React SPA (frontend2) поверх REST API

## Статус

Принято 2026-09-24 (эпик TRU-78, инфраструктура — TRU-79). Заменяет раздел
«Frontend» и связанные с ним последствия [ADR-002](adr-002-stack-repo-api)
(серверный рендеринг Django-шаблонами + jQuery). Остальное в ADR-002
(backend, формат API `/api/v1/`, хостинг) действует.

## Контекст

По ADR-002 веб делался Django-шаблонами + jQuery внутри `backend/`. К концу
M1 в команде появилось React-приложение `frontend2/` (Vite, Tailwind,
react-router, JWT), на котором уже сделаны календарь, список и карточка
ребёнка, группы и настройки. Держать два интерфейса к одним данным дорого:
каждое правило пришлось бы делать дважды. Команда решила перейти на
`frontend2` целиком.

## Решение

- **Веб — одностраничное React-приложение `frontend2/`.** Все новые экраны
  — только там. Старые Django-страницы переносятся и работают параллельно,
  пока переезд не закончится (эпик TRU-78), затем удаляются одним тикетом
  (TRU-88).
- **Фронт ходит только в REST API `/api/v1/` с JWT.** Сессионные
  веб-эндпоинты (`/clients/children/data/` и т.п.) фронт не использует: на
  их место делается DRF-эндпоинт, логика выносится в сервис, общий для API
  и старого веба (не копируется).
- **Токены.** Вход — `POST /api/v1/users/auth/login/`, продление —
  `POST /api/v1/users/auth/refresh/` (SimpleJWT, ротация refresh и
  blacklist). Access живёт 30 минут, refresh — 7 дней. Общий клиент
  `frontend2/src/api/axios.js` подставляет токен и при 401 сам продлевает
  его (одно продление на все одновременные запросы); протух refresh —
  выход на `/login`. Организация берётся из claim `organization_id` токена
  (`TenantMiddleware`).
- **Права** проверяются на API; фронт скрывает меню и кнопки по
  `permissions` из `/api/v1/users/auth/me/` — это удобство, не защита.
- **Раздача.** nginx отдаёт собранный `frontend2/dist` на `/` (SPA-фолбэк
  на `index.html`), проксирует на Django `/api/`, `/admin/`, `/static/`,
  `/media/` и старые страницы (`infra/nginx/app.conf`). Образ nginx сам
  собирает фронт (`infra/nginx/Dockerfile`) — один и тот же образ
  локально, в CI и на staging. Отдельного хостинга/CDN не нужно.
- **CI.** Джоб `frontend`: `npm ci`, `npm run lint` (oxlint),
  `npm run build`; джоб `build` собирает образ nginx с фронтом.
- **Языки.** На старте интерфейс `frontend2` только на русском (ТЗ п. 10.1:
  русский с первого дня, казахский — бэклог). Словари старого веба
  (`backend/i18n_src/{ru,kk,en}.json`) сохраняются и подключаются во
  фронт отдельной задачей, когда до казахского дойдёт очередь.

## Отвергнутые варианты

| Вариант | Почему нет |
|---|---|
| Оставить Django-шаблоны + jQuery (ADR-002) | Команда уже пишет экраны на React; два интерфейса к одним данным — двойная работа и расхождение правил. |
| React внутри Django-шаблонов (островки) | Та же двойная инфраструктура, но без плюсов SPA: роутинг, состояние и сборка всё равно нужны, а сессия и JWT смешиваются. |
| Отдельный хостинг фронта (CDN, Vercel и т.п.) | Лишний компонент инфраструктуры и CORS; nginx уже стоит перед backend и отдаёт статику бесплатно. |
| SSR (Next.js) | Все экраны за авторизацией, SEO не нужен; Node-runtime в проде — лишнее (как и в ADR-002). |

## Последствия

- В репозитории есть Node-тулчейн (`frontend2/package.json`); для запуска
  всего проекта Node на машине не нужен — фронт собирается в Docker.
- Каждому экрану нужен DRF-эндпоинт; права, изоляция тенантов и
  производительность проверяются тестами на API, а не на страницах.
- До TRU-88 старые страницы доступны по адресам со слешем на конце
  (`/clients/children/`, `/groups/`, `/settings/organization/`, вход
  `/login/`); React-маршруты — без слеша (`/children`, `/groups`,
  `/settings/organization`, вход `/login`).
- Новые вкладки карточки ребёнка и другие точки расширения описываются как
  React-контракты в `docs/contracts.md` (TRU-82), а не Django-фрагменты.
